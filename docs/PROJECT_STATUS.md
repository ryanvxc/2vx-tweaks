## Summary

The foundation is strong and the product is empty. The shell, dashboard, monitoring sampler and the whole safety
engine (journal, plan/apply/verify/rollback/revert, elevation broker, policy denylist, metadata gate) are implemented
and tested. But **no tweak is registered, no screen can apply or revert anything, and six of eight pages are
placeholders.** The engine has never been exercised by a user, and its UAC path has never been run end to end.

## Risks

1. **Unexercised engine.** The most safety-critical code has only been driven by tests. The first real use may
   expose UX or model problems (for example, per-snapshot revert only).
2. **UAC path untested.** The broker launch, the PID handshake under real elevation and an elevated write need a
   manual run on a VM.
3. **Primitive generalisation.** Power plans, services and QoS all need the journal to store more than registry
   targets. Doing this after the first UI slice avoids designing it blind.
4. **Documented-only rule vs tweak supply.** Several popular tweaks have no Microsoft documentation. Policy CSP / ADMX
   settings are documented with exact registry paths and are the most reliable source for the first set, at the cost
   of Windows showing "managed by your organization" on affected Settings pages.
